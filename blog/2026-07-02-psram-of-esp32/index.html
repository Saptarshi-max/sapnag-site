I Built a Message Broker for IoT — Here’s How to Run It With Live Grafana Monitoring

02 Jul 2026 in Blog

A hands-on walkthrough of MetricMQ: what it does differently, how to run the Python demos line by line, and how to watch your messages flow in real time through Prometheus and Grafana.

I kept running into the same wall building IoT systems: existing brokers are either too heavy for microcontrollers (RabbitMQ needs a full server) or too simple to be trustworthy (basic Redis pub/sub drops messages silently and has no security at the message level). So I built MetricMQ — a lightweight broker with a 16-byte binary protocol, built-in Ed25519 message signing, and a Prometheus metrics endpoint baked directly into the binary.

This post is a complete walkthrough. By the end you’ll have the broker running, all six core features demonstrated through Python, and a live Grafana dashboard showing your message traffic in real time. I’ll break down every piece of code so you understand not just what to run but why it works the way it does.

What a Message Broker Actually Does

Before touching any code, it helps to be clear on the problem.

Imagine you have a dozen ESP32 sensors publishing temperature readings, plus a database, a mobile dashboard, and an alert system that all want that data. Without a broker, every sensor needs a direct connection to every consumer:

Without a broker — messy, hard to scale:

  Sensor 1 ──→ Dashboard
  Sensor 1 ──→ Database
  Sensor 1 ──→ Alert System
  Sensor 2 ──→ Dashboard
  Sensor 2 ──→ Database
  Sensor 2 ──→ Alert System
  (12 sensors × 3 consumers = 36 connections to manage)

With MetricMQ — clean hub-and-spoke:

  Sensor 1 ──┐
  Sensor 2 ──┤──→ [ MetricMQ Broker :6379 ] ──→ Dashboard
  Sensor 3 ──┘                               ──→ Database
                                              ──→ Alert System

Sensors publish messages to named topics like sensors/temperature. Consumers subscribe to the topics they care about. The broker handles all the routing. Nobody needs to know about anybody else — you can add a new consumer without touching a single sensor.

Why MetricMQ and Not MQTT or Redis?

Honest comparison:

  MQTT Redis Pub/Sub NATS MetricMQ
Binary size ~500KB+ Separate server ~20MB 328KB
ESP32 compatible Yes, but TLS is heavy Not designed for MCUs No Yes — 2KB RAM client
Message-level signing No (TLS only) No No Ed25519 per message
Prometheus built in Via sidecar Via sidecar Via sidecar Native, no sidecar
Sequence numbers No No Yes Yes

Two things are genuinely different here — not just marketing claims:

Ed25519 per-message signing. MQTT and Redis rely on TLS for all security. TLS is expensive on microcontrollers — the handshake alone can take hundreds of milliseconds on an ESP32. MetricMQ embeds a 64-byte cryptographic signature directly in every message header. The broker verifies it before routing. A tampered or unsigned message is rejected and counted in Prometheus as metricmq_signature_failures_total. You can literally watch attacks in your dashboard.

Dual-protocol on the same port. The broker reads the first byte of every new connection and auto-detects whether it’s the MetricMQ binary protocol or Redis RESP text. An ESP32 using the C++ binary client and a Python script can publish and subscribe on the same topic namespace with zero configuration. This is why the demo uses plain Python sockets — no client library needed.

Two decisions worth explaining here:

The Wire Protocol — What’s Actually Happening Under the Hood

Before looking at the Python demo, it helps to understand how clients talk to MetricMQ. Every message is wrapped in a 16-byte binary header:

Byte position:  0      1      2-9        10-11      12-15
                ┌──────┬──────┬──────────┬──────────┬──────────┐
                │ Ver  │ Cmd  │ Sequence │ TopicLen │ PayloadLen│
                │ (1B) │ (1B) │  (8B)    │   (2B)   │   (4B)   │
                └──────┴──────┴──────────┴──────────┴──────────┘
                followed by: [Topic bytes] [Payload bytes]

This fixed-size header is one of MetricMQ’s core design decisions. Compare it to MQTT’s variable-length encoding — MQTT uses a complex multi-byte length field that requires branching logic to parse. MetricMQ’s header is always exactly 16 bytes, always the same structure. An ESP32 can parse it with a single struct read — no dynamic memory allocation, no parsing state machine.

The Cmd field tells the broker what to do:

0x01 = SUBSCRIBE  (client wants to receive messages on a topic)
0x03 = PUBLISH    (client is sending a message)
0x04 = MESSAGE    (broker delivering a message to a subscriber)
0x06 = PING       (keep-alive check)
0x07 = PONG       (keep-alive response)

The Sequence field is an 8-byte counter that the broker increments for every message. It’s stored in LMDB (an embedded database) so it survives broker restarts. If the broker crashes at sequence 5000 and restarts, the next message gets sequence 5001 — not 1. Subscribers can detect gaps.

The Python Demo — Line by Line

The demo script talks directly to MetricMQ using raw sockets and the 16-byte binary protocol. No broker-specific client library needed. Here’s how it’s structured, piece by piece.

The Frame Builder

import socket, struct, threading, time, json, random
from datetime import datetime

HOST = "127.0.0.1"
PORT = 6379
HEADER_SIZE    = 16
PROTO_VERSION  = 0x01
CMD_SUBSCRIBE  = 0x01
CMD_PUBLISH    = 0x03
CMD_MESSAGE    = 0x04
CMD_PING       = 0x06
CMD_PONG       = 0x07

These constants mirror the broker’s internal definitions exactly. PROTO_VERSION = 0x01 tells the broker which version of the protocol we’re speaking. If you ever update the protocol, clients on old versions get rejected cleanly rather than silently misbehaving.

def build_frame(cmd, topic, payload=b"", seq=0):
    t = topic.encode("utf-8")
    p = payload.encode("utf-8") if isinstance(payload, str) else payload
    return struct.pack(">BBQHL", PROTO_VERSION, cmd, seq, len(t), len(p)) + t + p

struct.pack(">BBQHL", ...) is where the 16-byte header gets assembled. The format string >BBQHL means:

  • > — big-endian byte order (network byte order, consistent across all platforms)
  • B — 1 unsigned byte (version)
  • B — 1 unsigned byte (command)
  • Q — 8 unsigned bytes (sequence number, fits up to 18 quintillion messages)
  • H — 2 unsigned bytes (topic length, up to 65535 characters)
  • L — 4 unsigned bytes (payload length, up to 4GB)

Total: 1+1+8+2+4 = 16 bytes exactly. Then the actual topic string and payload bytes are appended directly after. The broker reads the header first, gets the lengths, then reads exactly that many bytes for topic and payload. No delimiters, no parsing ambiguity.

The Frame Reader

def recv_exactly(sock, n):
    buf = bytearray()
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            raise EOFError()
        buf += chunk
    return bytes(buf)

TCP does not guarantee that one send() equals one recv(). The network can split a 16-byte header across two packets, or merge multiple messages into one buffer. recv_exactly loops until it has exactly n bytes — not more, not less. This is called framing and it’s essential for any binary protocol.

def read_frame(sock):
    raw = recv_exactly(sock, HEADER_SIZE)
    ver, cmd, seq, tlen, plen = struct.unpack(">BBQHL", raw)
    topic   = recv_exactly(sock, tlen).decode("utf-8") if tlen else ""
    payload = recv_exactly(sock, plen)                  if plen else b""
    return {"cmd": cmd, "seq": seq, "topic": topic, "payload": payload}

First read exactly 16 bytes. Unpack them according to the same format string used in build_frame — this is the mirror operation. Then read exactly tlen bytes for the topic and plen bytes for the payload. Return a clean dictionary. The broker does exactly the same thing on its side to parse incoming messages from clients.

The Client Class

class Client:
    def __init__(self, name):
        self.name     = name
        self._seq     = 0
        self._lock    = threading.Lock()
        self.received = []
        self.sock     = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        self.sock.connect((HOST, PORT))

socket.AF_INET means IPv4. socket.SOCK_STREAM means TCP — a reliable, ordered connection. Each Client instance is one TCP connection to the broker. The moment .connect() is called, the broker logs New client connected: fd=XXX.

The _lock is a threading mutex. The listen() method runs in a background thread (reading incoming messages), while the main thread can simultaneously call publish(). Without the lock, two threads could write to the socket at the same time and corrupt the data stream.

    def subscribe(self, topic):
        self._seq += 1
        self._send(build_frame(CMD_SUBSCRIBE, topic, seq=self._seq))

Subscribing is just sending a frame with CMD_SUBSCRIBE and the topic name. The payload is empty — the broker only needs the topic string to register this client as a subscriber. After this, any message published to this topic (or a matching wildcard) gets delivered to this socket.

    def publish(self, topic, payload):
        self._seq += 1
        self._send(build_frame(CMD_PUBLISH, topic, payload, self._seq))

Publishing sends CMD_PUBLISH with the topic and payload. The broker receives this, looks up all subscribers matching the topic, and delivers a copy to each one. The _seq here is the client’s sequence counter — separate from the broker’s global sequence counter.

    def listen(self, stop_event):
        try:
            while not stop_event.is_set():
                self.sock.settimeout(1.0)
                try:
                    frame = read_frame(self.sock)
                    if frame["cmd"] == CMD_MESSAGE:
                        inner = frame["payload"]
                        if len(inner) >= HEADER_SIZE:
                            _, _, seq, tlen, plen = struct.unpack(">BBQHL", inner[:HEADER_SIZE])
                            off     = HEADER_SIZE
                            topic   = inner[off:off+tlen].decode("utf-8", errors="replace")
                            payload = inner[off+tlen:off+tlen+plen].decode("utf-8", errors="replace")
                        else:
                            topic   = frame["topic"]
                            payload = inner.decode("utf-8", errors="replace")
                        self.received.append({"topic": topic, "payload": payload, "seq": frame["seq"]})
                    elif frame["cmd"] == CMD_PING:
                        self._send(build_frame(CMD_PONG, "", seq=frame["seq"]))
                except socket.timeout:
                    continue
        except (EOFError, OSError):
            pass

This runs in a background thread, constantly reading frames from the socket. Three things worth noting:

sock.settimeout(1.0) — the socket blocks for at most 1 second waiting for data. Without this, read_frame would block forever if no messages arrive, and the thread could never check stop_event.is_set() to know it should exit.

The CMD_MESSAGE branch handles delivered messages. MetricMQ wraps the delivered message as an inner frame inside the outer delivery frame’s payload. So we unpack the outer frame first, then unpack again from the payload bytes to get the actual topic and message content.

The CMD_PING branch responds to keep-alive pings from the broker. The broker sends a PING every 60 seconds to check if the client is still alive. If the client doesn’t respond with PONG, the broker closes the connection and decrements metricmq_active_connections.

Running All Six Features

Run the full script:

python metricmq_demo.py

Or run it in a continuous loop to generate enough data for the Grafana graphs:

while ($true) { python metricmq_demo.py; Start-Sleep 2 }

Here’s what each feature does and what MetricMQ mechanism it exercises.

Feature 1 — Basic Pub/Sub

def demo_pubsub():
    # Create two separate TCP connections to the broker
    sub = Client("subscriber-1")
    pub = Client("publisher-1")

    # Start the listener thread for the subscriber
    stop = threading.Event()
    threading.Thread(target=sub.listen, args=(stop,), daemon=True).start()

    # Register the subscriber's interest in this topic
    sub.subscribe("sensors/temperature")
    time.sleep(0.5)  # wait for subscribe to register before publishing

Two clients, two separate TCP connections. The time.sleep(0.5) after subscribing is important — the subscribe frame needs to reach the broker and be registered before any messages are published. Without this pause, the publisher might send messages before the broker knows the subscriber exists, and they’d be dropped.

    for i in range(1, 6):
        payload = json.dumps({"msg": i, "temp": round(20.0 + random.uniform(-2, 5), 1), "unit": "C"})
        pub.publish("sensors/temperature", payload)
        print(f"  [{ts()}] PUB  → sensors/temperature  {payload}")
        time.sleep(0.5)

    time.sleep(1.0)  # wait for all deliveries to arrive
    print(f"\n  ✅ Received {len(sub.received)}/5 messages")
    for m in sub.received:
        print(f"     [{ts()}] RECV ← {m['topic']}  {m['payload']}")

The payload is JSON — a human-readable format that works on both the ESP32 (C++ JSON parser) and Python. The broker doesn’t care what the payload contains — it’s opaque bytes as far as routing is concerned.

Expected output:

[00:02:40] PUB  → sensors/temperature  {"msg": 2, "temp": 21.8, "unit": "C"}
...
✅ Received 5/5 messages

Feature 2 — Wildcard Subscriptions

def demo_wildcard():
    sub = Client("wildcard-sub")
    pub = Client("wildcard-pub")
    stop = threading.Event()
    threading.Thread(target=sub.listen, args=(stop,), daemon=True).start()

    # Subscribe to a wildcard pattern — catches ALL subtopics under sensors/
    sub.subscribe("sensors/#")
    time.sleep(0.5)

    # Publish to four completely different subtopics
    topics = ["sensors/temperature", "sensors/humidity", "sensors/pressure", "sensors/co2"]
    for topic in topics:
        payload = json.dumps({"value": round(random.uniform(10, 100), 1)})
        pub.publish(topic, payload)
        print(f"  [{ts()}] PUB  → {topic}  {payload}")
        time.sleep(0.4)

The subscriber never named sensors/humidity, sensors/pressure, or sensors/co2 explicitly. It only said sensors/#. The # is a wildcard that matches any continuation of the path — including multiple levels deep, so sensors/room1/temperature would also match.

This matters in real IoT deployments. If you have a monitoring dashboard subscribed to sensors/#, you can add new sensor types to your network and they automatically appear in the dashboard. No reconfiguration, no redeployment.

Expected output:

Subscribed to: sensors/#
[00:02:44] PUB  → sensors/temperature  {"value": 73.7}
[00:02:44] PUB  → sensors/humidity     {"value": 13.7}
[00:02:45] PUB  → sensors/pressure     {"value": 82.8}
[00:02:45] PUB  → sensors/co2          {"value": 75.5}

✅ Wildcard caught 4/4 messages across all subtopics

Feature 3 — Fan-out

def demo_fanout():
    N    = 5
    # Create 5 independent subscriber clients (5 separate TCP connections)
    subs = [Client(f"fan-sub-{i}") for i in range(N)]
    pub  = Client("fan-pub")
    stops = [threading.Event() for _ in range(N)]

    # Each subscriber gets its own listener thread
    for i, sub in enumerate(subs):
        threading.Thread(target=sub.listen, args=(stops[i],), daemon=True).start()
        sub.subscribe("broadcast/alert")
    time.sleep(0.5)

    # One publish — broker delivers to all 5
    payload = json.dumps({"alert": "high_temp", "value": 87.3})
    pub.publish("broadcast/alert", payload)
    print(f"  [{ts()}] PUB  → broadcast/alert  {payload}")
    time.sleep(1.0)

    received = sum(1 for s in subs if len(s.received) > 0)
    print(f"\n  ✅ Fan-out: {received}/{N} subscribers received the message")

The broker maintains an internal map of topic → [list of subscriber connections]. When a publish arrives for broadcast/alert, the broker iterates that list and writes a copy of the message to each socket. The publisher sent one frame; five deliveries happened.

This is the mechanism behind alert systems, live dashboards, and logging pipelines — one event source, many consumers, zero coordination between consumers required.

What to watch in Prometheus: metricmq_messages_published_total increases by 1. metricmq_messages_delivered_total increases by 5. The ratio tells you the average fan-out factor.

Feature 4 — Sequence Numbers

def demo_sequence():
    sub = Client("seq-sub")
    pub = Client("seq-pub")
    stop = threading.Event()
    threading.Thread(target=sub.listen, args=(stop,), daemon=True).start()
    sub.subscribe("stream/data")
    time.sleep(0.5)

    # Send 8 messages as fast as possible
    for i in range(8):
        pub.publish("stream/data", json.dumps({"index": i}))
        time.sleep(0.05)  # 50ms between sends — fast but not instant

    time.sleep(1.0)
    print(f"  ✅ Received {len(sub.received)}/8 in order:")
    for m in sub.received:
        data = json.loads(m['payload'])
        print(f"     broker_seq={m['seq']}  index={data.get('index','?')}")

Each received message has a broker_seq — the broker’s global sequence counter at the time of delivery. Watch the numbers:

Expected output:

✅ Received 8/8 in order:
   broker_seq=4808  index=0
   broker_seq=4809  index=1
   broker_seq=4810  index=2
   broker_seq=4811  index=3
   broker_seq=4812  index=4
   broker_seq=4813  index=5
   broker_seq=4814  index=6
   broker_seq=4815  index=7

No gaps in the sequence numbers — 4808, 4809, 4810.... If you ever saw 4808, 4810 with 4809 missing, a message was dropped. The broker’s sequence numbers make that immediately visible.

Now stop the broker (Ctrl+C) and restart it. The first line of broker output will be:

Restored sequence counter from persistence: 4816

The next message after restart gets sequence 4816, not 1. This is LMDB doing its job — the sequence counter is persisted to disk after every message, so broker crashes don’t reset the counter and create ambiguous sequence numbers.

Feature 5 — Per-Topic Routing and Prometheus Labels

def demo_multi_topic():
    pub = Client("topic-pub")

    # Publish deliberately different counts to each topic
    topics = {
        "sensors/temperature": 10,
        "sensors/humidity":     6,
        "commands/actuator":    4,
        "logs/system":          8,
    }
    for topic, count in topics.items():
        for i in range(count):
            pub.publish(topic, json.dumps({"i": i}))
        print(f"  [{ts()}] {count:2d} msgs → {topic}")

Feature 6 — Connection Tracking

def demo_connections():
    clients = []
    for i in range(5):
        clients.append(Client(f"conn-{i}"))
        print(f"  [{ts()}] +1 connected  (total: {i+1})")
        time.sleep(0.3)  # stagger connections so Prometheus captures each step

    # Hold all 5 open for 3 seconds
    # Prometheus scrapes every 5s — this window ensures at least one scrape
    # captures metricmq_active_connections = 5
    time.sleep(3)

    for i, c in enumerate(clients):
        c.close()
        print(f"  [{ts()}] -1 disconnected  (remaining: {len(clients)-i-1})")
        time.sleep(0.3)

Every Client() constructor calls sock.connect(), which the broker counts. Every client.close() closes the TCP connection, which the broker detects via a socket read returning zero bytes.

The time.sleep(0.3) between each connection and disconnection is deliberate — it staggers the changes so the Grafana graph shows a visible staircase pattern (0→1→2→3→4→5→4→3→2→1→0) rather than a single spike.

What to watch in Grafana: The Active Connections stat panel steps up from 0 to 5, holds for 3 seconds, then steps back down. This is how you’d detect a reconnect storm in production — a spike in metricmq_connections_total with a corresponding spike in metricmq_disconnections_total a few seconds later.

Reading the Dashboard

After running the demo loop for a few minutes, here’s what the panels tell you:

Active Connections / Active Subscribers — live gauges. During Feature 6 you’ll see these climb to 5 then drop to 0.

Total Published = Total Delivered — the important one. If these numbers ever diverge, messages were dropped. Across thousands of publishes in the demo, they stay identical — zero delivery loss.

Publish Rate — shows bursts during the demo runs, flat between runs. The y-axis is messages per second, calculated by Prometheus using rate() over the last 1 minute.

P99 Publish Latency — the 99th percentile of publish operation time. On Windows loopback this sits around 60–100ms due to Python socket overhead. On actual hardware with the C++ client it drops to microseconds.

Messages per Topic — each topic gets its own coloured line. You can see Feature 5’s deliberate imbalance (10 messages to temperature, 4 to actuator) as different line heights.

Published vs Delivered — the two lines track each other exactly when everything is healthy. In a system with overloaded subscribers you’d see delivered lag behind published — an early warning before messages start backing up.

Useful PromQL Queries to Explore

Open http://localhost:9090 and try these directly:

# Live publish rate in messages per second
rate(metricmq_messages_published_total[1m])

# P99 latency — 99% of messages were published faster than this value
histogram_quantile(0.99, rate(metricmq_publish_latency_seconds_bucket[1m]))

# Per-topic breakdown — which topics are busiest
sum by (topic) (rate(metricmq_topic_messages_total[1m]))

# Delivery loss ratio — should be exactly 0.0 under normal conditions
1 - (metricmq_messages_delivered_total / metricmq_messages_published_total)

# Client churn — how fast are clients connecting and disconnecting
rate(metricmq_connections_total[5m])

# Security check — any rejected messages (should be 0 unless under attack)
rate(metricmq_errors_total[1m])

What’s Next

Everything above covers the transport and observability layers. The piece not shown here is the security layer — publishing a message to a secure/* topic without a valid Ed25519 key and watching the broker reject it. That’s the feature no equivalent lightweight broker has, and it’s visible in Prometheus as metricmq_signature_failures_total incrementing.

The ESP32 client is also worth wiring up once you have a device handy. The broker auto-detects the binary protocol from the first byte — the same Python demo running on your PC and a C++ client running on an ESP32 can both publish to the same topic, and both show up in the same Grafana dashboard. That combination — firmware and backend in one monitoring view — is what MetricMQ is built for.
