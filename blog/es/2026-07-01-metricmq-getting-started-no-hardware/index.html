Getting Started with MetricMQ: Local Setup and Grafana Monitoring

01 Jul 2026 in Blog / Embedded Software , Tags: C++

MetricMQ is a 328 KB C++20 message broker featuring a 16-byte binary protocol, Ed25519 message signing, LMDB sequence persistence, native Prometheus metrics, and an ESP32 client. This guide covers running the broker, testing Python demos, and visualizing real-time metrics with Prometheus and Grafana.

A technical guide to running MetricMQ, understanding its wire protocol, executing Python client demos, and setting up Prometheus and Grafana for real-time message tracking.

I built MetricMQ because existing message brokers often represent trade-offs when working with low-power microcontrollers. Full-featured brokers like RabbitMQ require significant system resources, while lightweight options like basic Redis pub/sub lack message-level security and persistent sequence tracking.

MetricMQ is a lightweight C++20 broker (328 KB binary) that uses a fixed 16-byte binary wire protocol, enforces optional per-message Ed25519 signature verification at the broker level, persists sequence IDs via LMDB for exact sequence tracking, and exposes a native Prometheus metrics endpoint on every path.

This post covers how to run the broker locally, execute Python scripts demonstrating its core feature set without external dependencies, and set up a Grafana dashboard to observe metrics in real time.

Message Broker Overview

A message broker decouples data producers (publishers) from data consumers (subscribers).

For example, when multiple microcontrollers record sensor data that needs to feed a database, a web dashboard, and an alerting service, connecting every sensor directly to every service scales poorly:

Direct connections (hard to scale):

  Sensor 1 ──→ Dashboard
  Sensor 1 ──→ Database
  Sensor 1 ──→ Alert System
  Sensor 2 ──→ Dashboard
  Sensor 2 ──→ Database
  Sensor 2 ──→ Alert System
  (12 sensors × 3 consumers = 36 connections)

Broker model (hub-and-spoke):

  Sensor 1 ──┐
  Sensor 2 ──┤──→ [ MetricMQ Broker :6379 ] ──→ Dashboard
  Sensor 3 ──┘                               ──→ Database
                                              ──→ Alert System

Publishers send messages to specified topic strings (e.g., sensors/temperature). Subscribers listen to topics of interest. The broker handles message routing so components can be added or removed independently.

Technical Comparison

Feature MQTT Redis Pub/Sub NATS MetricMQ
Binary size ~500 KB+ Separate server ~20 MB 328 KB
ESP32 compatible Heavy (TLS overhead) No No Yes (2 KB RAM client)
Message signing No (TLS transport only) No No Ed25519 per message
Prometheus metrics Requires exporter Requires exporter Requires exporter Native HTTP endpoint
Sequence numbers No No Yes Yes (LMDB persisted)

Key architectural differences:

  1. Message-level Ed25519 signatures: Standard MQTT relies entirely on TLS for security. TLS handshakes add substantial latency and memory pressure on microcontrollers. MetricMQ can include a 64-byte signature directly in the binary message header. The broker validates the signature prior to routing. Failed signatures are rejected immediately and increment the metricmq_signature_failures_total counter.
  2. Dual-protocol single-port handler: Upon establishing a TCP socket connection, the broker reads the initial byte to detect whether the client is sending MetricMQ binary frames or Redis RESP text. A microcontroller sending binary frames and a Python script using Redis protocol commands can publish to and consume from the same topics simultaneously.

The broker binary handles message routing on TCP port 6379 and serves Prometheus metrics on HTTP port 9091. A Prometheus instance running in Docker scrapes port 9091 every 5 seconds. Grafana queries Prometheus on port 9090 and renders the dashboard UI on port 3001.

@"
global:

  - job_name: 'metricmq'

      - targets: ['host.docker.internal:9091']

  • scrape_interval: 5s provides granular time-series resolution during local testing.

Wire Protocol Specification

MetricMQ uses a fixed 16-byte header for all binary frames:

Byte position:  0      1      2-9        10-11      12-15
                ┌──────┬──────┬──────────┬──────────┬──────────┐
                │ Ver  │ Cmd  │ Sequence │ TopicLen │ PayloadLen│
                │ (1B) │ (1B) │  (8B)    │   (2B)   │   (4B)   │
                └──────┴──────┴──────────┴──────────┴──────────┘
                Followed by: [Topic bytes] [Payload bytes]

Using a fixed-width 16-byte header simplifies parsing on resource-constrained platforms compared to variable-length header structures. Memory allocation can be completely avoided when receiving packets into static buffers.

Supported command byte values (Cmd):

  • 0x01 (SUBSCRIBE): Register interest in a topic.
  • 0x03 (PUBLISH): Send a message payload to a topic.
  • 0x04 (MESSAGE): Broker delivery of a payload to a subscriber.
  • 0x06 (PING): Connection keep-alive request.
  • 0x07 (PONG): Connection keep-alive response.

The 8-byte Sequence field contains a monotonic 64-bit integer maintained by the broker using LMDB, ensuring continuity across process restarts.

Python Client Implementation

The demo client uses standard Python libraries (socket, struct) to construct protocol frames directly.

Framing Utility

import socket, struct, threading, time, json, random
from datetime import datetime

HOST = "127.0.0.1"
PORT = 6379
HEADER_SIZE    = 16
PROTO_VERSION  = 0x01
CMD_SUBSCRIBE  = 0x01
CMD_PUBLISH    = 0x03
CMD_MESSAGE    = 0x04
CMD_PING       = 0x06
CMD_PONG       = 0x07

def build_frame(cmd, topic, payload=b"", seq=0):
    t = topic.encode("utf-8")
    p = payload.encode("utf-8") if isinstance(payload, str) else payload
    return struct.pack(">BBQHL", PROTO_VERSION, cmd, seq, len(t), len(p)) + t + p

struct.pack(">BBQHL", ...) builds the header:

  • >: Big-endian network byte order.
  • B: 1-byte protocol version (0x01).
  • B: 1-byte command code.
  • Q: 8-byte unsigned sequence number.
  • H: 2-byte unsigned topic length.
  • L: 4-byte unsigned payload length.

Socket I/O Helpers

def recv_exactly(sock, n):
    buf = bytearray()
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            raise EOFError()
        buf += chunk
    return bytes(buf)

def read_frame(sock):
    raw = recv_exactly(sock, HEADER_SIZE)
    ver, cmd, seq, tlen, plen = struct.unpack(">BBQHL", raw)
    topic   = recv_exactly(sock, tlen).decode("utf-8") if tlen else ""
    payload = recv_exactly(sock, plen)                  if plen else b""
    return {"cmd": cmd, "seq": seq, "topic": topic, "payload": payload}

recv_exactly handles TCP packet segmentation by reading until the buffer reaches requested length n.

Client Class Structure

class Client:
    def __init__(self, name):
        self.name     = name
        self._seq     = 0
        self._lock    = threading.Lock()
        self.received = []
        self.sock     = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        self.sock.connect((HOST, PORT))

    def _send(self, data):
        with self._lock:
            self.sock.sendall(data)

    def subscribe(self, topic):
        self._seq += 1
        self._send(build_frame(CMD_SUBSCRIBE, topic, seq=self._seq))

    def publish(self, topic, payload):
        self._seq += 1
        self._send(build_frame(CMD_PUBLISH, topic, payload, self._seq))

    def listen(self, stop_event):
        try:
            while not stop_event.is_set():
                self.sock.settimeout(1.0)
                try:
                    frame = read_frame(self.sock)
                    if frame["cmd"] == CMD_MESSAGE:
                        inner = frame["payload"]
                        if len(inner) >= HEADER_SIZE:
                            _, _, seq, tlen, plen = struct.unpack(">BBQHL", inner[:HEADER_SIZE])
                            off     = HEADER_SIZE
                            topic   = inner[off:off+tlen].decode("utf-8", errors="replace")
                            payload = inner[off+tlen:off+tlen+plen].decode("utf-8", errors="replace")
                        else:
                            topic   = frame["topic"]
                            payload = inner.decode("utf-8", errors="replace")
                        self.received.append({"topic": topic, "payload": payload, "seq": frame["seq"]})
                    elif frame["cmd"] == CMD_PING:
                        self._send(build_frame(CMD_PONG, "", seq=frame["seq"]))
                except socket.timeout:
                    continue
        except (EOFError, OSError):
            pass

    def close(self):
        try:
            self.sock.close()
        except OSError:
            pass

listen() runs in a background thread with a 1.0-second socket timeout to permit non-blocking shutdown checks via stop_event. It also handles broker PING requests by returning a PONG response frame.

Core Feature Demos

1. Basic Publish / Subscribe

def demo_pubsub():
    sub = Client("subscriber-1")
    pub = Client("publisher-1")

    stop = threading.Event()
    threading.Thread(target=sub.listen, args=(stop,), daemon=True).start()

    sub.subscribe("sensors/temperature")
    time.sleep(0.5)

    for i in range(1, 6):
        payload = json.dumps({"msg": i, "temp": round(20.0 + random.uniform(-2, 5), 1), "unit": "C"})
        pub.publish("sensors/temperature", payload)
        print(f"  [{ts()}] PUB  → sensors/temperature  {payload}")
        time.sleep(0.5)

    time.sleep(1.0)
    print(f"\n  ✅ Received {len(sub.received)}/5 messages")
    for m in sub.received:
        print(f"     [{ts()}] RECV ← {m['topic']}  {m['payload']}")

2. Wildcard Topic Filtering

def demo_wildcard():
    sub = Client("wildcard-sub")
    pub = Client("wildcard-pub")
    stop = threading.Event()
    threading.Thread(target=sub.listen, args=(stop,), daemon=True).start()

    sub.subscribe("sensors/#")
    time.sleep(0.5)

    topics = ["sensors/temperature", "sensors/humidity", "sensors/pressure", "sensors/co2"]
    for topic in topics:
        payload = json.dumps({"value": round(random.uniform(10, 100), 1)})
        pub.publish(topic, payload)
        print(f"  [{ts()}] PUB  → {topic}  {payload}")
        time.sleep(0.4)

The multi-level wildcard # matches any hierarchy trailing the specified topic prefix.

3. Subscriber Fan-Out

def demo_fanout():
    N    = 5
    subs = [Client(f"fan-sub-{i}") for i in range(N)]
    pub  = Client("fan-pub")
    stops = [threading.Event() for _ in range(N)]

    for i, sub in enumerate(subs):
        threading.Thread(target=sub.listen, args=(stops[i],), daemon=True).start()
        sub.subscribe("broadcast/alert")
    time.sleep(0.5)

    payload = json.dumps({"alert": "high_temp", "value": 87.3})
    pub.publish("broadcast/alert", payload)
    print(f"  [{ts()}] PUB  → broadcast/alert  {payload}")
    time.sleep(1.0)

    received = sum(1 for s in subs if len(s.received) > 0)
    print(f"\n  ✅ Fan-out: {received}/{N} subscribers received the message")

The broker duplicates published messages across all matching subscriber sockets. In Prometheus, metricmq_messages_published_total increments by 1 while metricmq_messages_delivered_total increments by N (5).

4. Sequence Number Verification

def demo_sequence():
    sub = Client("seq-sub")
    pub = Client("seq-pub")
    stop = threading.Event()
    threading.Thread(target=sub.listen, args=(stop,), daemon=True).start()
    sub.subscribe("stream/data")
    time.sleep(0.5)

    for i in range(8):
        pub.publish("stream/data", json.dumps({"index": i}))
        time.sleep(0.05)

    time.sleep(1.0)
    print(f"  ✅ Received {len(sub.received)}/8 in order:")
    for m in sub.received:
        data = json.loads(m['payload'])

def demo_multi_topic():

def demo_connections():
    clients = []
    for i in range(5):
        clients.append(Client(f"conn-{i}"))
        print(f"  [{ts()}] +1 connected  (total: {i+1})")
        time.sleep(0.3)

PromQL Queries for Verification

Useful queries for checking metric states in Prometheus (http://localhost:9090):

# Overall publish throughput in msg/sec
rate(metricmq_messages_published_total[1m])

# 99th percentile publish latency
histogram_quantile(0.99, rate(metricmq_publish_latency_seconds_bucket[1m]))

# Message throughput grouped by topic
sum by (topic) (rate(metricmq_topic_messages_total[1m]))

# Unacknowledged or dropped message ratio (0 under normal operation)
1 - (metricmq_messages_delivered_total / metricmq_messages_published_total)

# Client connection attempt rate
rate(metricmq_connections_total[5m])

# Signature validation failure rate
rate(metricmq_errors_total[1m])
