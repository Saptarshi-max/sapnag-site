Getting Started with MetricMQ

Audience: Beginner to intermediate embedded developers and IoT enthusiasts.  

Hardware used: 2× ESP32-S3-DevKitC-1-N16R8, Windows PC.  

What you will build: A two-board sensor telemetry system with delivery guarantees, wildcard routing, and cryptographic message signing — running on a broker smaller than most JPEGs.

1. The Problem with “Just Use MQTT”

You have two microcontrollers on your desk. You want them to talk to each other through your laptop. Someone on the internet tells you to “just use MQTT.”

So you install Mosquitto. You write a broker config. You fight the firewall. You try to figure out why redis-cli can’t connect to port 1883. An hour later you have a broker running, and you realise you still haven’t written a single line of application code.

This is the gap MetricMQ was built to fill.

On one end you have fire-and-forget solutions — raw UDP, basic MQTT QoS 0 — fast and simple, but no delivery guarantees. On the other end you have RabbitMQ and Kafka: reliable, but these are 50 MB+ server applications that want a config file, a dedicated port, and ideally a dedicated ops person.

MetricMQ sits between them. The broker is a 328 KB single executable. The ESP32 client uses under 2 KB of RAM at idle. It gives you exactly-once delivery, Ed25519 message signing, Prometheus metrics, and it speaks Redis’s text protocol — so redis-cli just works against it out of the box.

No Docker. No YAML. No certificate authority.

2. When Should You Use MetricMQ?

MetricMQ is the right tool when:

  • You are building an IoT sensor network and need to know that readings actually arrived — not just fire-and-forget.

  • You want a local broker that runs on the same PC as your development environment without standing up a server.

  • You need per-device cryptographic identity so that a compromised sensor cannot inject fake readings into your system.

  • You want live metrics on message rates and latency without writing any extra code.

  • Your devices are resource-constrained — the ESP32 client fits comfortably alongside your application code.

MetricMQ is not the right tool if you need TLS-encrypted payloads (it signs but does not encrypt — add a VPN if confidentiality is required), if you need to connect to an existing MQTT infrastructure, or if you need more than 1,000 simultaneous connections.

3. Key Features at a Glance

Before touching any code, here is what the library actually provides.

Dual Protocol with Auto-Detection

MetricMQ serves two protocols on the same port (6379):

Protocol Use Case Overhead

|—|—|—|

RESP (Redis text protocol) Debugging, scripting, redis-cli Human-readable
Binary (MetricMQ native) Embedded devices, production 16-byte header, ~40% smaller on wire

The broker reads the first byte of every connection and routes accordingly. You do not configure anything — a redis-cli client and an ESP32 binary client can talk through the same broker simultaneously.

Exactly-Once Delivery

Every published message gets a monotonically increasing sequence ID. The subscriber sends an ACK frame. The broker persists ACK state to an embedded LMDB database. If the subscriber disconnects and reconnects, the broker replays only the messages that were never acknowledged — no duplicates, no gaps.

Ed25519 Message Signing

MetricMQ uses libsodium Ed25519 for message authentication. Each device has a 32-byte public key and a 64-byte secret key. The publisher signs every message; the broker verifies the signature before routing. Topics prefixed with secure/ reject unsigned publishes at the wire level — before they reach any subscriber.

Subscribers can also verify signatures locally, without trusting the broker. This means even a compromised broker cannot inject fake signed messages.

Built-In Observability

A Prometheus-compatible HTTP endpoint runs on port 9091. Point any Prometheus scraper or just curl at it:


http://localhost:9091/metrics

You get message rates, active connections, latency histograms (p50/p99/p99.9), per-topic counters, and ACK efficiency — all with zero extra configuration.

Lightweight LMDB Storage

All messages are written to an embedded LMDB key-value database before delivery. Random reads hit 1.56 million ops/s. The database compacts automatically every 1,000 publishes, so it never grows unboundedly.

6. Step 0 — Find Your PC’s IP Address

Both boards need to know your PC’s local IP address. Open PowerShell:


ipconfig | Select-String "IPv4"

Note the address (e.g., 192.168.1.100). You will paste this into both sketches.

7. Step 1 — Build and Start the Broker


cd C:\Users\Sapta\Documents\Projects\MetricMQ

  

# Build (if not already done)

cmake --build build --config Release --target metricmq-broker

  

# Start the broker

.\build\Release\metricmq-broker.exe

You will see:


MetricMQ broker starting on port 6379

Prometheus metrics on port 9091

Leave this terminal open. The broker runs until you press Ctrl+C.

To verify it is working before touching any board:


# In a second terminal — subscribe via redis-cli (or sub_only.exe)

redis-cli -p 6379 SUBSCRIBE sensors/test

  

# In a third terminal — publish a test message

redis-cli -p 6379 PUBLISH sensors/test "hello"

You should see "hello" appear in the subscriber terminal. That confirms the broker is running correctly.

11. Project Walkthroughs

The publisher sketch automatically progresses through three phases. Here is what each one demonstrates and what to look for.

Project 1 — Basic Sensor Telemetry (0 to 60 seconds)

What happens: Board #1 publishes a JSON payload to sensors/esp32/telemetry every 5 seconds.

What to observe:

  • Board #2 Serial Monitor prints each incoming message with its sequence number.

  • The broker terminal logs the connection and message count.

  • Open http://localhost:9091/metrics in a browser and watch metricmq_messages_published_total increment.

The code behind it (simplified):


// Publisher side — Board #1

MetricMQClient pub;

pub.connect(BROKER_HOST, 6379);

  

String payload = "{\"temp\":22.3,\"hum\":54.2,\"rssi\":" + String(WiFi.RSSI()) + "}";

pub.publishSigned("sensors/esp32/telemetry", payload.c_str());



// Subscriber side — Board #2

MetricMQClient sub;

sub.connect(BROKER_HOST, 6379);

  

sub.subscribe("sensors/esp32/#", [](const char* topic,

                                     const uint8_t* payload, size_t len,

                                     uint64_t seq) {

    Serial.printf("MSG seq=%llu  topic=%s\n", seq, topic);

    Serial.printf("  %.*s\n", (int)len, payload);

});

This is the baseline IoT data flow. Two boards, one broker, one API call each.

Project 2 — High-Frequency Burst Mode (60 to 90 seconds)

What happens: The publisher ramps up to one message per second on sensors/esp32/burst.

What to observe:

  • Messages arrive at Board #2 at 1 Hz. Watch the sequence numbers increment continuously.

  • Check http://localhost:9091/metrics — metricmq_publish_latency_us will show live latency histograms.

  • Binary protocol wire size: a 90-byte JSON payload produces a 106-byte frame (16-byte header + topic + payload). An equivalent RESP frame would be ~180 bytes. That ~40% reduction matters when you are pushing data over a congested WiFi channel.

What this demonstrates: The binary protocol is not just a micro-optimisation. At 1 message/second with a 90-byte payload, the binary protocol saves around 74 bytes per message — roughly 4.4 KB/minute of saved bandwidth per device. In a 20-node sensor network running on battery-backed WiFi, that adds up.

Project 3 — Multi-Topic Fan-Out with Wildcards (90+ seconds)

What happens: The publisher sends to three separate topics every 5 seconds:

  • sensors/esp32/temperature

  • sensors/esp32/humidity

  • sensors/esp32/status

Board #2, subscribed to sensors/esp32/#, receives all three with a single subscription.

What to observe:

  • The subscriber Serial Monitor shows messages arriving on three different topic paths, all caught by one wildcard.

  • Per-topic message counts are visible at /metrics under metricmq_topic_messages_total.

The code behind it:


// Publisher — one call per topic

pub.publishSigned("sensors/esp32/temperature", "{\"celsius\":22.3}");

pub.publishSigned("sensors/esp32/humidity",    "{\"percent\":54.2}");

pub.publishSigned("sensors/esp32/status",      "{\"rssi\":-45}");



// Subscriber — one wildcard catches all three

sub.subscribe("sensors/esp32/#", onMessage);

This is the routing model that makes MetricMQ useful for multi-sensor deployments. You can add a third board publishing to sensors/esp32/vibration and Board #2 will receive it automatically — no subscriber code changes required.

Project 4 — Cross-Protocol Communication (Bonus)

What happens: You publish from your PC using the RESP text protocol (redis-cli), and Board #2 receives it over its binary protocol connection.

Open a new terminal while both boards are running:


redis-cli -p 6379 PUBLISH sensors/esp32/telemetry "{\"source\":\"desktop\",\"value\":99}"

Watch Board #2’s Serial Monitor — that message arrives on the same wildcard subscription, indistinguishable from messages sent by Board #1.

What this demonstrates: The broker routes messages by topic regardless of what protocol each client used to connect. A Python script, a redis-cli one-liner, and an ESP32 all participate in the same message bus. Useful for injecting test data, sending commands from a laptop, or bridging to legacy tooling that only speaks Redis.

Project 5 — Ed25519 Signed Publishing (Advanced)

What happens: You generate a per-device Ed25519 keypair for Board #1. The publisher signs every message with its 64-byte secret key. The broker verifies the signature before routing. Board #2 verifies the signature again locally — without trusting the broker.

Step A — Generate a Keypair


.\build\Release\metricmq-keygen.exe "sensor_node_1" "secure/sensors/*"

The tool prints:

  • A C array for the secret key → paste into SecurePublisher.ino

  • A C array for the public key → paste into SecureSubscriber.ino and the broker registration

  • Broker registration code → add to src/main.cpp before the broker starts

Step B — Register the Key in the Broker

The keygen tool prints the exact snippet to paste into src/main.cpp:


// In main(), before broker.run():

uint8_t sensor_node_1_pk[32] = { 0xAB, 0xCD, /* ... 32 bytes ... */ };

broker.get_keystore().register_key(1, sensor_node_1_pk, {"secure/sensors/*"});

Rebuild and restart the broker after this change.

Step C — Use the Secure Examples

Flash SecurePublisher.ino to Board #1 and SecureSubscriber.ino to Board #2. You will see this in Board #2’s Serial Monitor:


[SIGNED ✓] Verified  topic=secure/sensors/temp  key_id=1

  Payload: {"celsius":22.3}

If anyone tampers with the payload in transit:


[SIGNED ✗] TAMPERING DETECTED — dropping message

If an unregistered device tries to publish to a secure/ topic:


[BROKER] Rejected: unknown key_id=999

You can also run the standalone desktop test to see all cases exercised:


.\build\Release\signed_publish_test.exe



[PASS] Valid signed message accepted

[PASS] Tampered payload rejected

[PASS] Unknown key rejected

[PASS] Disabled key rejected

[PASS] Wrong topic scope rejected

All 9/9 tests passed

Important note: Ed25519 authenticates — it proves the message came from the device that holds the secret key. It does not encrypt. The payload bytes are visible on the wire. If you need confidentiality, run the broker behind a VPN or add stunnel. Authentication and encryption are separate concerns.

12. Resilience Testing — The “Pull the Plug” Test

This is where exactly-once delivery becomes concrete rather than theoretical.

Test 1: Unplug the Subscriber

  1. While both boards are running (Phase 1 or 3), unplug Board #2 from USB.

  2. Board #1 keeps publishing. The broker keeps assigning sequence IDs and persisting messages to LMDB.

  3. Plug Board #2 back in. It reconnects, re-subscribes, and the broker replays every unacknowledged message from where it left off.

  4. Board #2’s Serial Monitor will show: Duplicates: 0 (exactly-once working!)

No messages lost. No duplicates. The sequence numbers are continuous.

Test 2: Restart the Broker

  1. Press Ctrl+C in the broker terminal to stop it.

  2. Wait 5 seconds. Both boards will log MetricMQ disconnected.

  3. Restart the broker: .\build\Release\metricmq-broker.exe

  4. Both boards reconnect automatically. The broker loads ACK state from LMDB on startup, so it knows exactly which messages each client has already processed.

Test 3: WiFi Interruption

  1. On your router, briefly disable and re-enable WiFi (or move a board far enough away to drop signal).

  2. Both boards detect the TCP disconnect and attempt reconnection.

  3. Once WiFi is restored, they reconnect and resume where they left off.

One honest caveat: The ESP32 client does not auto-reconnect by itself — your sketch must check isConnected() and call connect() manually. Both demo sketches do this in loop(). If you write your own sketch, copy that pattern:

```cpp

void loop() {

    if (!client.isConnected()) {

        client.connect(BROKER_HOST, BROKER_PORT);

    }

    client.loop();

    // … your application code

}

```

14. Understanding the Numbers

The README claims 106,000 messages/second and 46.5 µs p50 latency. Those numbers are real — but they were measured on a loopback interface on a developer machine. Here is what to expect in practice:

Scenario Realistic expectation

|—|—|

ESP32 over WiFi, 1 subscriber 500–2,000 msg/s
ESP32 over WiFi, 5 subscribers 200–500 msg/s
Desktop loopback (binary protocol) 80,000–106,000 msg/s
p50 latency, loopback ~46 µs
p50 latency, ESP32 over WiFi 2–15 ms

For a sensor polling at 1 Hz or even 10 Hz, the WiFi numbers are more than sufficient. The benchmark figures matter for desktop or Linux server deployments where you are pushing high-volume data pipelines.

The 328 KB binary size comparison is straightforward: Mosquitto is ~1.5 MB, a minimal Node.js MQTT server pulls in ~15 MB of node_modules, RabbitMQ starts at 50 MB. MetricMQ fits on a USB stick next to a README.

15. Troubleshooting

Symptom Probable cause Fix

|—|—|—|

ESP32 won’t connect to WiFi 5 GHz network ESP32 only supports 2.4 GHz
Connection refused on broker port Broker not running or firewall Start the broker; add inbound rule for TCP 6379 in Windows Firewall
Wrong BROKER_HOST IP changed after router restart Re-run ipconfig and update both sketches
Board not detected in Arduino Missing USB driver Install CP210x or CH340 driver for your board’s USB chip
Upload fails with “Connecting…” Boot mode Hold the BOOT button on the board while clicking Upload; release after “Connecting…” appears
PSRAM not detected Wrong board setting Set PSRAM: OPI PSRAM in Tools menu, not “Disabled”
Subscriber shows 0 messages Both boards must use identical BROKER_HOST Verify with Serial Monitor output
MDB_MAP_FULL in broker logs LMDB database full This should not occur under normal use (auto-compacts at 100K messages); if it does, delete metricmq.db and restart

16. When NOT to Use MetricMQ

Being honest about limits builds trust more than overselling:

  • You need TLS-encrypted payloads — MetricMQ signs but does not encrypt. Use a VPN layer or stunnel if the data must be confidential in transit.

  • You need MQTT QoS 1/2 compatibility — If your project must speak standard MQTT to existing infrastructure, use Mosquitto.

  • You need more than 1,000 concurrent connections — MetricMQ has a hard cap of 1,000 simultaneous connections by design.

  • You need RESP authentication — The RESP protocol has no credentials. Any device that can reach port 6379 can publish. Restrict access at the firewall for any production LAN deployment.

17. What to Explore Next

You have a working two-board system with delivery guarantees, wildcard routing, and live metrics. Here is what to try next:

Queue Mode (Push/Pull) — Instead of broadcast pub/sub, use QueueProducer and QueueConsumer for round-robin task distribution across multiple workers. Useful for offloading computation from sensor nodes.


// Desktop producer pushes jobs

metricmq::QueueProducer prod("127.0.0.1", 6379);

prod.push("jobs/process", "{\"sensor_id\":\"node_01\",\"raw\":1042}");

  

// Multiple ESP32 workers pull and process one-at-a-time

metricmq::QueueConsumer worker("127.0.0.1", 6379);

worker.pull("jobs/process", [](const std::string& payload) {

    process(payload);

});

Wokwi Simulation — The wokwi/ folder in the repo contains browser-simulatable projects. You can run the demo without any physical hardware using wokwi.com.

Grafana Dashboard — Point Prometheus at localhost:9091, import a dashboard, and get live graphs of message rates, latency percentiles, and per-device topic counts.

Multiple Secure Devices — Each ESP32 gets its own keypair. The broker’s TrustedKeyStore holds each device’s public key scoped to its own topic prefix. One call to set_enabled(key_id, false) to instantly revoke a compromised device — no certificate rotation, no infrastructure changes.

Summary

MetricMQ is not trying to replace Kafka or compete with cloud IoT platforms. It is trying to answer a specific question: what is the simplest possible setup that still gives you delivery guarantees, device identity, and observability?

The answer turns out to be a 328 KB binary, a 50-line Arduino sketch, and a redis-cli command to verify it is working.

The two-board demo in this guide runs everything locally, requires no accounts, no cloud services, and no configuration files beyond updating three constants in a sketch. That is the point.
